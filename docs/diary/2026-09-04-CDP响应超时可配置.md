# 2026-09-04 CDP 响应超时可配置

Issue #3 修复日：`DEFAULT_IPC_RESPONSE_TIMEOUT_SECONDS = 5.0` 对所有 CDP 往返硬编码,慢站导航与 agent Chrome 冷启动叠加时 `Page.navigate` 超 5 秒即抛 `_IPCResponseTimeout`,把「还没回来」误报成「拿不到」(用户实测:google_search 触发冷启动后,people.com.cn / sohu / zh.wikipedia 首轮全灭,数分钟后环境热了一次过)。

修复三层,全走「截图 60s 先例」的同款结构:

1. **普通预算可配**——`BH_IPC_TIMEOUT` 覆盖默认 5s;
2. **导航单独预算**——新增 `NAVIGATE_IPC_RESPONSE_TIMEOUT_SECONDS`(默认 30s,`BH_NAVIGATE_TIMEOUT` 可调),由 `goto_url` 携带;`extract_url_content`/`new_tab`/workspace 应用全经 `goto_url`,一处修复全链受益,用户 workaround(workspace 覆盖 `goto_url` 传 `_response_timeout=30`)可退役;
3. **截图预算顺带可配**——`BH_SCREENSHOT_TIMEOUT` 覆盖 60s,三个预算一个 `_env_seconds` 解析(空/不可解析/非正数一律回退默认——config 手误不能炸 module import)。

验证:单测 +3(goto_url 携带导航预算断言镜像截图测试、`_env_seconds` 五分支、import 期 env 覆盖经 `importlib.reload` 证实含恢复性回滚),全树 268 绿;dev 真栈 `--once` 冷启动两连——issue 原失败站点 zh.wikipedia.org 一次过(预算 5/30/60 生效),`BH_NAVIGATE_TIMEOUT=7.5` 活体改值生效 + `wait_for_load` 后标题落定。[实证: 2026-09-04 Windows dev 栈 9225]

文档随动:SKILL Gotchas 补 IPC 预算条目(三副本同步)+ `.env.example` 补三变量 + TODO 行。

## 自省

- **issue 的 workaround 反向指认了最小修点**:用户没在 workspace 里包一层重试,而是覆盖 `goto_url` 传 `_response_timeout`——说明阻塞点收敛在导航这一个调用,而不是全线慢。顺着 workaround 找修点比顺着报错找快:报错在 `_send`(底层),根因在 `goto_url`(调用面预算错配)。
- **默认参数冻结时机的老朋友**:`cdp`/`_send` 的默认参数在 def 时冻结,好在 `_load_env()` 在常量定义前执行,env 派生值天然进默认;`goto_url` 里则是调用期全局查找,monkeypatch 直接可测。两种时机都对了才让测试没绕弯。

## 导航三态事件判定(同日二追,用户定向架构原则)

上一追发出去后用户给出原则修正:**超时只是兜底,所有操作应事件驱动——事件是准确状态的判官(成功/失败/未知),超时只在无事件时防死锁**。对照盘点:wait_for_network_idle 已纯事件驱动;wait_for_load/wait_for_element 是状态轮询(超时返 False,不冒充失败,可接受);**唯一违规是 goto_url——IPC 响应超时直接 raise,把「未知」伪装成「失败」**,这正是 Issue #3 语义层的根因。

落地:`Page.navigate` 的响应本身就是状态事件(commit→frameId / errorText→失败),响应丢失(IPC 超时)后由 daemon 缓冲事件流接管判定——主帧 `Page.frameNavigated`(过滤子帧与后台会话)→成功(事件带重定向后最终 URL),`chrome-error:`→失败,页面 URL 精确佐证→成功(事件被并发 drain 吃掉时的兜底),静默到点→`verdict unknown ... may still be in flight` 如实抛出。原则入 SKILL Design Constraints(三副本)。+5 单测,256 绿。

dev 真栈三态活体实证 [实证: 2026-09-04 Windows dev 栈 9225]:①快站(wikipedia/people.com.cn)响应先回,原路径无回归;②本地 3s 慢回服务器 + `BH_NAVIGATE_TIMEOUT=0.2` 强制丢响应 → 事件/状态判成功 `{'url':..., 'late': True}`;③本地挂死服务器(accept 后永不响应)→ 5.2s 得 `verdict unknown ... may still be in flight`,不伪装失败。

自省:原则修正来的时机刚好——第一追修的是「预算长度」(30s 代替 5s),治标;这一追修的是「超时的语义角色」(判官→兜底),治本。如果先把原则问清楚,第一追会直接做成三态。教训:**涉及等待/重试/超时的设计,先对齐「谁判状态、超时算什么」的语义,再调参数**。遗留排后:wait_for_load 等待原语事件化(TODO 队列「等待原语事件化」)。
