# 2026-09-04 CDP 响应超时可配置

Issue #3 修复日：`DEFAULT_IPC_RESPONSE_TIMEOUT_SECONDS = 5.0` 对所有 CDP 往返硬编码,慢站导航与 agent Chrome 冷启动叠加时 `Page.navigate` 超 5 秒即抛 `_IPCResponseTimeout`,把「还没回来」误报成「拿不到」(用户实测:google_search 触发冷启动后,people.com.cn / sohu / zh.wikipedia 首轮全灭,数分钟后环境热了一次过)。

修复三层,全走「截图 60s 先例」的同款结构:

1. **普通预算可配**——`BH_IPC_TIMEOUT` 覆盖默认 5s;
2. **导航单独预算**——新增 `NAVIGATE_IPC_RESPONSE_TIMEOUT_SECONDS`(默认 30s,`BH_NAVIGATE_TIMEOUT` 可调),由 `goto_url` 携带;`extract_url_content`/`new_tab`/workspace 应用全经 `goto_url`,一处修复全链受益,用户 workaround(workspace 覆盖 `goto_url` 传 `_response_timeout=30`)可退役;
3. **截图预算顺带可配**——`BH_SCREENSHOT_TIMEOUT` 覆盖 60s,三个预算一个 `_env_seconds` 解析(空/不可解析/非正数一律回退默认——config 手误不能炸 module import)。

验证:单测 +3(goto_url 携带导航预算断言镜像截图测试、`_env_seconds` 五分支、import 期 env 覆盖经 `importlib.reload` 证实含恢复性回滚),全树 268 绿;dev 真栈 `--once` 冷启动两连——issue 原失败站点 zh.wikipedia.org 一次过(预算 5/30/60 生效),`BH_NAVIGATE_TIMEOUT=7.5` 活体改值生效 + `wait_for_load` 后标题落定。[实证: 2026-09-04 Windows dev 栈 9225]

文档随动:SKILL Gotchas 补 IPC 预算条目(三副本同步)+ `.env.example` 补三变量 + TODO 行。

## 自省

- **issue 的 workaround 反向指认了最小修点**:用户没在 workspace 里包一层重试,而是覆盖 `goto_url` 传 `_response_timeout`——说明阻塞点收敛在导航这一个调用,而不是全线慢。顺着 workaround 找修点比顺着报错找快:报错在 `_send`(底层),根因在 `goto_url`(调用面预算错配)。
- **默认参数冻结时机的老朋友**:`cdp`/`_send` 的默认参数在 def 时冻结,好在 `_load_env()` 在常量定义前执行,env 派生值天然进默认;`goto_url` 里则是调用期全局查找,monkeypatch 直接可测。两种时机都对了才让测试没绕弯。

## 导航三态事件判定(同日二追,用户定向架构原则)

上一追发出去后用户给出原则修正:**超时只是兜底,所有操作应事件驱动——事件是准确状态的判官(成功/失败/未知),超时只在无事件时防死锁**。对照盘点:wait_for_network_idle 已纯事件驱动;wait_for_load/wait_for_element 是状态轮询(超时返 False,不冒充失败,可接受);**唯一违规是 goto_url——IPC 响应超时直接 raise,把「未知」伪装成「失败」**,这正是 Issue #3 语义层的根因。

落地:`Page.navigate` 的响应本身就是状态事件(commit→frameId / errorText→失败),响应丢失(IPC 超时)后由 daemon 缓冲事件流接管判定——主帧 `Page.frameNavigated`(过滤子帧与后台会话)→成功(事件带重定向后最终 URL),`chrome-error:`→失败,页面 URL 精确佐证→成功(事件被并发 drain 吃掉时的兜底),静默到点→`verdict unknown ... may still be in flight` 如实抛出。原则入 SKILL Design Constraints(三副本)。+5 单测,256 绿。

dev 真栈三态活体实证 [实证: 2026-09-04 Windows dev 栈 9225]:①快站(wikipedia/people.com.cn)响应先回,原路径无回归;②本地 3s 慢回服务器 + `BH_NAVIGATE_TIMEOUT=0.2` 强制丢响应 → 事件/状态判成功 `{'url':..., 'late': True}`;③本地挂死服务器(accept 后永不响应)→ 5.2s 得 `verdict unknown ... may still be in flight`,不伪装失败。

自省:原则修正来的时机刚好——第一追修的是「预算长度」(30s 代替 5s),治标;这一追修的是「超时的语义角色」(判官→兜底),治本。如果先把原则问清楚,第一追会直接做成三态。教训:**涉及等待/重试/超时的设计,先对齐「谁判状态、超时算什么」的语义,再调参数**。遗留排后:wait_for_load 等待原语事件化(TODO 队列「等待原语事件化」)。

## agent Chrome 恢复气泡根治(同日三追,用户报告)

搜索验收跑到一半用户报告:agent Chrome **每次启动都弹「未正确关闭,恢复页面?」**。根因一层:所有停机路径(teardown/看门狗/chrome-mode 翻转)都汇到 `_stop_agent_chrome` 按 pid 杀,而 Windows 的 `os.kill(pid, SIGTERM/SIGKILL)` 全是 `TerminateProcess` 硬杀——Chrome 永远没机会写干净退出标记,profile 的 `exit_type` 恒留 `Crashed`,下次启动必弹恢复气泡。修法:kiosk 标准姿势 `_normalize_chrome_exit_type`(Chrome 确认停止后 + 拉起锁内 Popen 前,把 `Preferences` 的 `exit_type` 归 `Normal`——拉起前那次还能修复断电/外来杀手留下的脏状态)+ `--hide-crash-restore-bubble` 旗标双保险(真崩溃也不唠叨)。+5 单测 278 绿;dev 真栈实证:修前 `exit_type = Crashed`(历史硬杀的债)→ 一轮 `--once` 冷启停 → `Normal`。

顺修 M110(单测逼出冷分支的意外收获):给「Chrome 杀不死」分支写单测时炸出 `signal.SIGKILL` 在 Windows 不存在——强杀升级路径一执行就 AttributeError,潜伏至今只因 Windows 首轮 TerminateProcess 必死、升级分支从未被走过。`getattr(signal, "SIGKILL", signal.SIGTERM)` 修平。自省:**平台分叉 API 的冷分支等于未测试分支**,让 `_agent_chrome_running` 恒 True 强走升级路径才现形;这也反证了「不只测 happy path」(AGENTS 规则 11)的现实回报。

## 任务级浏览器隔离 + Browser.close 优雅关闭(同日五追,用户定向架构)

用户定向两连:「每个任务默认操作单独的浏览器,不要多任务倒腾一个浏览器的多个 tab」+「任务隔离应该有 Chrome CDP 正规的关闭浏览器方式,研究下」。两问答案经确认:--once/--batch 自动隔离(持久栈不动)、隔离浏览器克隆基础登录 profile(不失登录态)。

**Browser.close 研究**(用户点名研究):daemon 的 ws 是 browser 级,`Browser.close` 直达且优雅——Chrome 自写干净退出状态(恢复气泡根治的另一半);**命令回复常因浏览器先拆而不达,成功判据必须是调试端口消亡**(事件判状态,回复丢失≠失败)。落地三层:daemon `meta:close_browser`(判定同款)、看门狗连带关(`_stop_agent_chrome_if_last` 优雅优先)、admin `_stop_agent_chrome` 分层(优雅→pid 兜底),teardown 反序——浏览器先优雅关(借还活着的 daemon)再停 daemon。

**任务隔离**(`task_isolation.py`,入口先于 admin/helpers import 绑 env,它们 import 期读 BU_NAME/端口/profile):task-<hex> daemon 名 + **9230+ 端口内核预留**(fd 持有到进程退出)+ 登录 profile 克隆(`*Cache*`/Service Worker 跳过,Windows 锁文件降级占位不中断)+ teardown 清场(守卫 task-profiles 根,误设 env 不会 rmtree 别处)。自钉 `BU_CDP_URL=127.0.0.1:<port>`——local 模式发现只认用户 Chrome PROFILES 与 9222/9223,不钉就猎到用户浏览器(M101/S004 红线)。

真栈验收三雷三修,每雷都是单测或对照实验逼出:①`CancelledError` 继承 BaseException 穿透 `except Exception`(FakeCDP 抛 CancelledError 的测试当场炸出);②`apply_from_argv` 先于 .env 载入判 pin,dev checkout(BU_CDP_URL 在 .env)被误隔离→端口错配 30s 死等;③并发双任务**端口 TOCTOU**——bind-后-close 探测窗口两任务同抢 9230,败者 daemon 挂上胜者的 Chrome,隔离被静默击穿(M109 同族第三犯,内核预留根治)。修后双任务双浏览器真并行(9230/9231 各自导航成功)+ teardown 全清场(task-profiles 0 残留、923x 监听 0、dev 栈 9225 不受扰)。另顺修 `wait_for_load` 单次轮询 IPC 超时即炸(冷启动首轮 evaluate 常>5s;单次轮询超时=未知,等待自身的 deadline 才是判官)+ 隔离任务默认 `BH_IPC_TIMEOUT=10` 冷启动余量。+9 单测 292 绿。

自省两则:其一,**我自己踩了 diary 里记过的坑**——bash `&` 把整条 `&&` 链背景化(09-03 自省原文),导致 rm -rf 与并行任务互咬,UO 一场;错误清单就在案头还是重犯,「记过」不等于「免疫」,写命令前应先扫一眼当日教训。其二,隔离被击穿的方式是**静默的**(两任务都"成功",只是共用了浏览器)——若只验「跑通」不验「端口互异」,TOCTOU 就带着隔离假象上线;验收并发隔离必须断言资源互斥性,不只断言功能成功。
