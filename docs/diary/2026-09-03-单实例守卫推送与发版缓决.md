## Issue #2 双模式对齐（同日追加）

第二条 Issue：heredoc 管道里 `web_fetch` NameError 而 `google_search` 可用。根因不是缺能力——web-fetch 的核心 `extract_url_content` 本就预导入——是「app 名 ↔ 函数名」映射靠运气：核心写在 agent_helpers 的（google/bing-search）有同名函数，写成纯 CLI 包装的（web-fetch）没有，核心在打包模块的（x-search）完全不可达。

用户定向把修复抬成原则：**stdin 模式与命令模式双兼容是 harness 类程序运行的核心逻辑**。落地三件：`run_app(name, *args, json_output)` 通用子命令桥（子进程复刻 CLI 语义，核心子命令与 app 通吃，按构造对齐、永不漂移）；`web_fetch()` 别名对齐 CLI 默认值（纯 HTTP 起步、bot 墙升级浏览器）；R003 §2 落「双模式兼容」条款（app 核心进 agent_helpers、脚本保持薄包装、能力不允许单边存在）。+5 单测（含复刻 issue 踩空链路的 `import *` 冒烟），227 绿。

自省：真栈 E2E 依旧欠——连续两条 Issue 都卡在「本 checkout dev `.env` 是 WSL 侧配置」上（Windows 侧跑 stdin 模式会以 `/home` 路径 profile 拉 Chrome 造脏目录），今日以 import 链冒烟 + 命令构造单测代偿，真栈验证挂到发版自验。环境反复挡路就该沉淀：TODO 挂「dev 环境 Windows 侧真栈姿势」（BH_HOME 指独立目录 + .env 平台分文件）。
