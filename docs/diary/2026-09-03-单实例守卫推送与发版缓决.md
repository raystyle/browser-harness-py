## Issue #2 双模式对齐（同日追加）

### 任务生命周期三分类与闲置看门狗（同日七追，用户定向）

用户定向两连：任务分**持久/批量/一次性**三类；持久任务也要闲置超时自动关浏览器。落地：`--once`/`--batch` 前缀旗标 = 调用级 teardown（**只拆自己冷启动的栈**——所有权旗标 `_launched_chrome_here`/`_started_daemon_here`，已在跑的栈永不被动）；持久默认 + daemon 侧 `_idle_watchdog`（`BH_IDLE_TIMEOUT` 默认 30 分钟，> x-monitor 10 分钟轮询故监控永不误退；请求即续活；触发走 meta:shutdown 同款优雅路径），末位 daemon 连带关 agent Chrome（先探活其他 daemon；远端/用户浏览器模型直接跳过）。+11 单测，248 绿；dev 真栈三场景实证（--once 即测即清、与装机栈共存不动对方、45s 闲置触发只关自己）。

顺修两条 E2E 抓出的存量竞态：①`os.kill(pid, 0)` 在 Windows 是 `CTRL_C_EVENT`——对分离态 daemon 误报「已死」、对控制台进程会真注入 Ctrl+C，`restart_daemon` 的死等循环因此瞬间放弃 → 端口文件被退出中的 daemon 短暂持锁 → `cleanup_endpoint` unlink 撞 `PermissionError` 直接炸任务（chrome-mode 翻转当日也呲过同款）。修法：`_pid_alive` 换 `OpenProcess(SYNCHRONIZE)` 探活 + unlink 带 10×50ms 重试容错（M109 锁下单写者，残留文件本就无害）。[实证: E2E 首跑崩、修复后同场景过]

**未解之谜挂待观察**：下午两例装机 9223 agent Chrome 消亡（一例在纯编码窗口、一例在 doctor 重拉后数分钟），用户明确否认手动关闭；新机制（teardown/看门狗/pid 匹配）逐一受控复现均阴性（dev-env `_agent_chrome_pids()` 实测只匹配自身 pid、装机 Chrome 在短超时看门狗触发下幸存）。两例均涉及 0.6.8 旧代码进程与 headed 实例，暂无从归因；复现再深挖（届时查 Windows 事件日志与 daemon 关 tab 链路）。
