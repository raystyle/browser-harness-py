# S006 WSL2 无头环境适配研究

> 研究原型过程（为什么）。登记日 2026-09-01。
> 来源：本机 WSL2 Ubuntu 24.04（mirrored 网络 + WSLg）/ Linux Chrome 152.0.7977.64 / rmux 0.10.0 实测。

## 结论速览

- WSL2 里跑通 browser-harness 全链路（daemon + web-fetch + 管道自动化 + 资源视图）只需四件事：装原生 Linux Chrome、launcher 行尾修 LF、agent 端口换 9224 避开 Windows 侧、`BH_CHROME_HEADLESS=1` 无头启动。[实证: 2026-09-01 本机 WSL 内 `--doctor` 全绿、web-fetch 抓取 example.com 成功、`goto_url`+`page_info` 管道自动化成功]
- **mirrored 网络下 WSL 与 Windows 共享 loopback**：WSL 内 `127.0.0.1:9223` 直达 Windows 侧 agent Chrome（实测返回 Chrome/154 Windows UA）。因此 WSL 侧 agent Chrome 必须换端口（选 9224），否则两栈撞车或互相误判「已在运行」。[实证: WSL 内 curl 9223 返回 Windows Chrome 版本信息]
- Linux 无头 Chrome（专用 user-data-dir + `--remote-debugging-port`）**没有 M144「Allow remote debugging」弹窗、没有 403**，`/json/version` 直接返回 webSocketDebuggerUrl——Windows 上那套 chrome://inspect 授权流程在无头专用 profile 场景完全不涉及。[实证: Chrome 152 headless 启动 4 秒后 CDP 即通]
- Chrome 在 Linux 上会**重写自己的 `/proc/<pid>/cmdline`**，重写后是空格连接而非 NUL 分隔，进程枚举按 NUL 切分会得到一整串。见 M104。[实证: /proc/6334/cmdline 读出单元素含全部 flags]

## 探索过程

### 尝试 1：复用 Windows 侧 agent Chrome（9223）

- 思路：mirrored 网络 loopback 互通，WSL 的 daemon 直接连 Windows 9223，零安装。
- 结果：连通性没问题 [实证: curl 返回 Windows Chrome 154 版本信息]。但放弃作为默认方案：两套 harness（Windows 栈 + WSL 栈）管一个浏览器会抢 tab，违背 S004 的隔离原则；且 Windows 栈停了 WSL 就瘫，不是自包含。
- 定位：作为「零安装临时接管」路径保留可行性，默认走 WSL 自包含。

### 尝试 2：WSL 内装 snap Chromium

- 思路：Ubuntu 惯例 `snap install chromium`。
- 结果：WSL 内没有 snapd，直接不可行；且 snap 封装本身破坏 CDP（见 `docs/snap-linux-headless.md`）。用 Google 官方 .deb。[实证: .deb 安装后即用]

### 尝试 3：launcher 直接跑

- 思路：`./browser-harness --doctor` 开跑。
- 结果：`/usr/bin/env: 'bash\r': No such file or directory`——Windows 侧 checkout 把工作区文件 smudge 成 CRLF，shebang 带 `\r`。`.gitattributes` 钉 `browser-harness`/`*.sh` 为 `eol=lf` 后重新 checkout 解决。[实证: 修后 `./browser-harness --version` 正常]

### 最终方案：WSL 自包含无头栈

`.browser-harness-dev/.env`（dev 模式）四个键：

```bash
BU_CDP_URL=http://127.0.0.1:9224        # 钉住 WSL 自己的 agent Chrome
BH_AGENT_CDP_PORT=9224                   # mirrored 网络：9223 归 Windows 侧
BH_CHROME_HEADLESS=1                     # 强制无头（WSLg 有 DISPLAY，自动检测不会触发，需显式）
BH_AGENT_CHROME_PROFILE=/home/ray/.cache/browser-harness/agent-chrome-profile  # ext4，不放 /mnt/d
```

代码侧改动（均已落单测）：

- `_agent_port()`：`BH_AGENT_CDP_PORT` 可配（默认 9223），`_pinned_agent_cdp` 跟随比较——自动拉起白名单与端口解耦。
- `_headless_flags()`：`BH_CHROME_HEADLESS=1` 强制无头（`--headless=new --disable-gpu`，root 追加 `--no-sandbox`）；`=0` 显式关；未设置时**无显示的 Linux 自动无头**（DISPLAY 与 WAYLAND_DISPLAY 均空）。
- `_launch_agent_chrome` 透传 `BH_CHROME_EXTRA_FLAGS`（与 `_launch_browser` 行为对齐）。
- `browsers` 资源视图补 Linux 枚举（`/proc` 扫描，含 M104 的空格连接 cmdline 兼容）。

## 注意事项

- 无头 UA 是 `HeadlessChrome/152...`，反爬敏感站点可能区别对待；需要时用 `BH_CHROME_EXTRA_FLAGS=--user-agent=...` 覆盖。[推断: UA 字段实测可见，站点行为未逐站验证]
- Chrome 152 无头自动补 `--ozone-platform=headless --ozone-override-screen-size=800,600`，实测视口 780×493；需要更大视口用 `--window-size` 覆盖。[实证: page_info 返回 w=780 h=493]
- x-monitor 在 WSL 可跑（rmux 就绪），但 agent profile 是全新的，X 登录态要在 9224 的 Chrome 里重新登一次（可临时 `BH_CHROME_HEADLESS=0` 起 WSLg 窗口登录，再切回无头）。[推断: 登录流程未在 WSL 实测]
- `/mnt/d`（DrvFS）上放 Chrome profile 慢且锁文件行为不稳，profile 一律放 ext4。[经验: Windows/WSL 双侧使用惯例]
