# S005 抓取 / 内容提取能力对比研究

> 研究原型过程（为什么）。登记日 2026-09-01。
> 来源：本仓库 `web-fetch`/`agent_helpers` 实测 + R001 资料（Defuddle / fetch-use / defuddle-fetch-mcp-server）。

## 结论速览

- 我们现有 `web-fetch` 用的是 **pydefuddle 0.1.0**（Python 移植），只有通用正文提取（`elements/`、`removals/`），**没有站点专用 extractor**。
- JS 原版 **Defuddle 0.19.3**（737 commits）内置 90+ 站点 extractor（github / twitter / youtube / reddit / medium 等），对特定站点的正文质量明显更强。
- `fetch-use==0.4.0` 依赖虽然装了，但 `web-fetch` 实际走的是 `urllib` 纯 HTTP（`_http_get`），**没用 fetch-use 的反爬/代理/stealth**。
- 结论：**需要增强**，优先补「站点专用提取」和「反爬抓取」。

## 现状 vs 参考

| 能力 | 我们现状 | 参考资料 | 差距 |
| --- | --- | --- | --- |
| 正文提取引擎 | pydefuddle 0.1.0（Python 移植） | Defuddle JS 0.19.3（737 commits） | 版本/能力滞后 |
| 站点专用 extractor | 无（只有通用 elements/removals） | 90+ 站点 extractor（github/twitter/youtube/reddit…） | 缺失 |
| 反爬 / 代理 / stealth | urllib 纯 HTTP + 可选 `use_browser=True` | fetch-use（真实浏览器 + 代理 + stealth） | 部分 |
| MCP 暴露 | 无（仓库有 mcp_server.py，但未接 web-fetch） | defuddle-fetch-mcp-server | 缺失（可选） |

## 关键实测

- `pydefuddle` 包结构只有 `elements/`、`removals/`，没有 `extractors/` 目录 → 确认无站点专用规则。
- `agent_helpers._http_get` 用 `urllib.request`；`fetch_use` 未被引用 → fetch-use 只是装而未用。

## 增强建议（按优先级）

1. **站点专用提取（高）**：给 `web-fetch` 引入站点 extractor。
   - 首选：复用 browser-harness 的 `domain-skills`（按站点沉淀提取规则），轻量、可 agent 生成。
   - 或：在 pydefuddle 通用流程上，对高频站点（X / GitHub / 新闻站）加专用选择器规则。
   - 不推荐：vendor 完整 JS Defuddle + linkedom（2-3MB、依赖树，收益不划算）。
2. **反爬抓取（中）**：`web-fetch` 对 bot-sensitive 页面自动走浏览器（`use_browser=True`）或 fetch-use；公开静态页保持纯 HTTP 快速路径。
3. **MCP（低）**：如后续要对 MCP 客户端暴露抓取，再补 `web-fetch` 的 MCP 工具（复用现有 `mcp_server.py`）。
